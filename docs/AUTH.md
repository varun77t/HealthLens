# Accounts, sessions and saved analyses

> **For research and educational purposes only. Predictions generated by this system are
> based on machine-learning models trained on historical public datasets and must not be
> interpreted as medical diagnosis or professional medical advice.**

Authentication is **mandatory**. No disease assessment, document upload, prediction,
explanation, report or history is reachable without a session. There is no anonymous
prediction path anywhere in the system.

Being signed in is **not** the same as being recorded. Signing in unlocks the flow; it does
not start a record. Health values reach the database only through the explicit save action
on the result screen, and `/predict/*` never writes at all.

---

## Setup

```bash
cp .env.example .env          # optional in development; every value has a default
python -m alembic upgrade head
```

The database defaults to SQLite at `data/app.db`, which is git-ignored — it holds password
hashes and any health values typed in while testing. `alembic upgrade head` is the only way
the schema is created; the application prints a loud warning and refuses to sign anyone in
if the tables are missing.

Production must set `ENV=production`, an explicit `ALLOWED_ORIGINS`, an https
`APP_BASE_URL` and a Postgres `DATABASE_URL`. `backend/settings.py:validate` refuses to
start otherwise — see [Configuration](#configuration).

## The design, and why

### Sessions are opaque tokens in an httpOnly cookie

A 256-bit random value from `secrets.token_urlsafe`, returned once in a `Set-Cookie` header
and stored only as its SHA-256 digest.

| | consequence |
|---|---|
| **Nothing is signed** | there is no key that could forge a session, and none to rotate |
| **A database dump is not credentials** | the digest cannot be replayed |
| **Deleting the row ends the session now** | no window where a token stays valid because it has not yet expired |
| **httpOnly** | unreadable from JavaScript, so an XSS cannot lift it |
| **The browser attaches it** | `<a href>` downloads (the demo reports) are authenticated for free |

The last row is not a small thing. With a bearer token every download link would have had to
become a fetch-and-blob dance, and any call that forgot the header would fail.

The alternative — a JWT in `localStorage` — trades revocability for a secret to protect. For
an application holding health information that is the wrong way round.

SHA-256 is the right hash for a session token and the wrong one for a password. The
difference is entropy: 256 random bits cannot be brute-forced whatever the hash costs, so
speed is free; a human-chosen password can be, so the hash must be deliberately slow.

### Passwords use argon2id, with pinned parameters

64 MiB, 3 passes, 4 lanes — RFC 9106's low-memory profile — set explicitly in
`backend/security.py` rather than inherited from the library, so upgrading `argon2-cffi`
cannot silently change the cost of every new hash. Existing hashes carry their own
parameters and are re-hashed on next sign-in when they fall behind.

### Both sign-in failures are identical

Same status, same message, same time. An unknown address still costs a full argon2
verification against a dummy hash — without it that path returns in microseconds and
response latency becomes an account-existence oracle that the shared error message does
nothing to close. A test asserts the floor.

`/auth/signup` is the one route that does disclose whether an address is registered. The
alternative needs reliable email delivery this deployment does not assume, and produces a
form that appears to succeed while creating nothing. Sign-in and password reset stay
non-disclosing, which is where an attacker with a list of addresses would actually go.

### Anything that changes a password ends the other sessions

Changing a password is what someone does *because* they think a session is compromised.
A reset ends **every** session, including the one that requested it: possession of a link
from an inbox is weaker evidence than knowing the password.

### Rate limits live in the database

`login_attempts` is a real table, not a process dictionary, so a limit survives a restart
and holds across workers — an in-memory counter disappears exactly when someone is hammering
the process hard enough to restart it.

| kind | window | per address | per source |
|---|---|---|---|
| `login` | 15 min | 5 failures | 20 failures |
| `signup` | 1 hour | — | 5 |
| `reset` | 1 hour | 3 | 10 |

A successful sign-in clears that address's failures, so an earlier fumble does not
accumulate toward a lockout. Limits are checked **before** the argon2 verification —
checking after would make the deliberately slow hash the denial of service.

`X-Forwarded-For` is believed only when `TRUST_PROXY_HEADERS` is set. A client can otherwise
put anything in it and present a new address per request, which would make every per-IP
limit a formality.

### Deletion is real

Hard `DELETE` with `ON DELETE CASCADE`, not a flag. A soft delete would leave the email
address and the saved health values in the table after someone asked for them to be removed,
which is not what the interface promises.

On SQLite, `ON DELETE CASCADE` does nothing unless `PRAGMA foreign_keys=ON` is issued **per
connection**. `backend/db.py` does it on every connect and
`test_sqlite_actually_enforces_the_cascade` holds the line, because the failure mode is
"delete my account" appearing to succeed while leaving every row behind.

## Routes

Public — and this is the whole list, pinned by `test_the_public_set_is_exactly_what_it_should_be`:

| method | path | |
|---|---|---|
| `GET` | `/health` | liveness probe |
| `GET` | `/` | service description and disclaimer |
| `POST` | `/auth/signup` | 201, sets the cookie |
| `POST` | `/auth/login` | 200, sets the cookie |
| `POST` | `/auth/logout` | 204, clears it whether or not the session resolved |
| `GET` | `/auth/me` | the user, or **204** when anonymous |
| `GET` | `/auth/sessions` | signed-in browsers |
| `POST` | `/auth/logout-all` | end every other session |
| `POST` | `/auth/password` | change password |
| `POST` | `/auth/forgot` | 202 always, whether or not the address exists |
| `POST` | `/auth/reset` | spend a reset link |
| `DELETE` | `/auth/account` | re-authenticated, then hard-deleted |

`/auth/me` answers **204 rather than 401** when nobody is signed in. The frontend calls it on
every page load to decide what to render; a 401 there would put an error in the console on
the landing page of a perfectly healthy application and train everyone to ignore it.

Everything else requires a session. Enforcement is one loop in `backend/main.py` attaching
`require_user` to whole routers, so an endpoint added to any of them is protected by default.
`tests/test_access_control.py` sweeps the routes the application actually registered and
asserts each answers 401 without a cookie — a router added to the wrong tuple fails the
suite rather than shipping open.

### Saved analyses

| method | path | |
|---|---|---|
| `POST` | `/analyses` | **inputs only** — the server re-runs the model and stores its own answer |
| `GET` | `/analyses` | your rows, newest first, `disease` / `limit` / `offset` |
| `GET` | `/analyses/{id}` | 404 for someone else's row, never 403 |
| `PATCH` | `/analyses/{id}` | the label, and nothing else |
| `DELETE` | `/analyses/{id}` | |

**The client never posts a probability.** A history assembled from what the browser claimed
would be a table of unprovenanced figures shown to someone as their own health record. The
save request has no field for a result, and a stray `probability` among the features is
rejected outright rather than silently dropped.

**Every row pins its threshold, band boundaries and model version.** A retrain moves the
operating threshold — diabetes's is 0.1388 — so a stored probability rendered against a
later threshold would reverse whether the model flagged the case. When the live version no
longer matches, the entry says so and offers a fresh assessment. Nothing is ever re-scored.

**Only the label is mutable.** The values and the result are a record of what was run, not a
draft. Changing an answer means running a new assessment — the same rule the review screen
has enforced since Phase 9.

Ownership is structural: `backend/services/analysis_store.py` has no lookup that does not
filter on the user, so there is no function that *could* serve one person's record to
another. Someone else's id returns 404, because a 403 confirms the id exists.

## What is stored

| table | contents |
|---|---|
| `users` | email, optional display name, argon2id hash |
| `user_sessions` | token digest, expiry, last-seen, browser description, IP |
| `password_resets` | token digest, expiry, used-at |
| `login_attempts` | the rate-limit ledger, pruned after two days |
| `analyses` | **only what was explicitly saved** — see below |

A saved analysis holds the feature values, the model's own output (probability, flag,
threshold, band, version, calibration, imputed fields, SHAP contributions, warnings), the
source kind, and the uploaded document's **filename**.

The uploaded document itself is never stored, and never logged. Nothing is written by
running an assessment: `tests/test_access_control.py` runs three predictions, a scenario and
a document upload and asserts every table's row count is unchanged.

**There is no encryption at rest.** That is a deployment property — Postgres on an encrypted
volume, or SQLCipher — not something this application can claim on its own. Field-level
encryption with a key sitting in `.env` beside the database would protect against
approximately nothing while letting the interface say "encrypted", so it is not done and the
account page says so plainly instead.

## Configuration

Everything is environment-driven; see `.env.example` for the full list with defaults.
`ENV=production` turns `backend/settings.py:validate` from warnings into a refusal to start:

- `ALLOWED_ORIGINS` must be set explicitly, must not be `*`, and must not be plain http
- `COOKIE_SECURE` must be true
- `APP_BASE_URL` must be https — reset links are built from it
- `DATABASE_URL` must not be SQLite
- interactive docs are off unless `DOCS_ENABLED` is set

**There is no application signing key.** Nothing is signed, so there is nothing to leak.

### Email

With no `SMTP_HOST`, `ConsoleMailer` prints the reset link to the server log. That is the
intended development behaviour rather than a fallback: the reset flow itself — single-use,
expiring, hashed, session-invalidating — is identical either way, and nothing about its
security depends on which mailer is active. Setting `SMTP_HOST` switches to real delivery.
