# Project Context — Multi-Disease AI

_State as of Phase 6 complete. Last updated 2026-09-02._

Orientation document: what this project is, what has been built, what every number in it
actually means, and what happens next. For the full phase-by-phase build log see
[`PROJECT_STATUS.md`](PROJECT_STATUS.md); this file is the condensed current state.

---

## 1. What this is

An **Explainable Multi-Disease Risk Prediction Platform**: three *fully independent*
disease pipelines — heart, kidney, diabetes — each with its own dataset, preprocessing,
feature set, models, evaluation and explainability layer.

**Deliberately not built:** a combined model, an "overall health score", or any cross-disease
aggregate. The three modules share code (`ml/`) but never share a model, a feature space or
a prediction.

### Non-negotiable positioning

This is a **research/education platform, not a medical diagnostic system**. Every artifact,
report, model card and (eventually) API response carries:

> For research and educational purposes only. Predictions generated by this system are based
> on machine-learning models trained on historical public datasets and must not be
> interpreted as medical diagnosis or professional medical advice.

Never claim: guaranteed diagnosis, medical certainty, clinical-grade prediction, treatment
recommendation, or that someone will develop a disease.

### Standing engineering rules

| rule | why |
|---|---|
| **No fabricated numbers.** Every metric, SHAP value and prediction comes from an actual run. | The whole project is worthless as a portfolio piece if a single number is invented. Enforced by `tests/test_model_artifacts.py`, which reloads each pipeline, re-scores the test split and asserts equality with `metrics.json`. |
| **No data leakage.** Preprocessing is never fitted before the split; SMOTE/resampling only inside the CV pipeline. | All preprocessing lives inside an `imblearn.Pipeline`, so it is fitted on training folds only. |
| **Calibration and thresholds are chosen on training data only.** | Choosing either on the test set makes the reported test metrics optimistic. See §5. |
| **Selection is never by accuracy.** | Composite rank = 0.4·ROC-AUC + 0.4·PR-AUC + 0.2·recall. |
| **Secrets never committed.** No `.env`, service keys or JWT secrets; sensitive model ops stay server-side. | — |
| `RANDOM_STATE = 42` everywhere; deps pinned; raw data cached. | Verified: retraining all three models reproduces byte-identical metrics. |

## 4. Model selection: **not one of the three choices is decisive**

All three runs report `decisive: false`, with the machine-generated reasons:

| disease | selected | runner-up | gap | fold std | why not decisive |
|---|---|---|---|---|---|
| heart | xgboost | logreg | 0.000495 | 0.0316 | gap below fold-to-fold std **and** below the 0.005 resolution floor |
| kidney | svc | random_forest | 0.000208 | 0.0000 | below resolution floor **and** both models saturated (>0.99) |
| diabetes | xgboost | lightgbm | 0.000259 | 0.0014 | gap below fold-to-fold std **and** below the resolution floor |

Read every leaderboard as *these models perform comparably*, not as a quality ranking. A
different random seed could reorder them. **The choice of algorithm is not a finding.**

Cross-validated ROC-AUC across the zoo:

- **heart** — logreg 0.9067, random_forest 0.9015, xgboost 0.8801, svc 0.8770, lightgbm 0.8583
- **kidney** — svc 1.0000, random_forest 0.9996, lightgbm 0.9990, logreg 0.9990, xgboost 0.9971
- **diabetes** — xgboost 0.8301, lightgbm 0.8288, logreg 0.8221, random_forest 0.8049

### A real bug this machinery caught (Phase 4)

The original `selection_margin` only compared the top-2 gap against fold-to-fold std. Kidney's
SVC scores **exactly 1.0 with std exactly 0.0**, so a 0.0002 gap satisfied `gap > std` and the
run reported the choice as *decisive* — the least trustworthy case possible, since zero std at
saturation means the metric has **no resolution left**, not that the estimate is precise.

`selection_margin` now checks three independent failure modes (below fold std, below the
0.005 resolution floor, both candidates above 0.99) and returns every reason to doubt.
`tests/test_selection_and_diagnostics.py` carries a regression test.

## 6. Why each score is what it is

The project runs probes that attribute performance rather than accepting it. These are meant
to be reported *especially* when the answer is unflattering.

### Kidney: missingness is confounded with the outcome — the headline 0.9987 is not clinical evidence

A **missingness-only probe** discards every measured value and trains logistic regression on
the 24 binary *is-this-value-missing* indicators alone:

| | ROC-AUC |
|---|---|
| missingness indicators only, 5-fold CV | **0.8600 ± 0.0445** |
| missingness indicators only, test | **0.8023** |
| full model, test | 0.9987 |

"Which labs were ordered" alone reaches 0.80. Supporting evidence
(`reports/kidney/missingness_vs_target.csv`): `rbc` missing → **94.1%** CKD vs 43.2% when
present; `rbcc` 94.7% vs 46.8%; `wbcc` 93.4% vs 51.4%; `pot` 94.3% vs 53.5%.

Complete-case analysis is not a fix: only **158/400 rows (39.5%)** are complete, and the
positive rate collapses from **0.625 → 0.2722** in that subset, discarding most of the
positive class.

Because imputation runs inside the pipeline, an imputed value *is* a marker that the test was
never ordered. **This is not train/test leakage — the split stays clean — but it is a hard
ceiling on transfer** to any setting where these labs are ordered routinely.

### Heart: the probe finds nothing, which is the good outcome

Missingness indicators alone reach test ROC-AUC **0.4394** (below chance; only 2 indicator
features, CV 0.500 ± 0.000) against the full model's 0.9535. 297/303 rows (98.0%) are
complete. The measurement pattern does **not** explain heart's performance.

### Diabetes: no missing values, but the feature set has a hard ceiling

No values are missing, so the measurement-pattern probe does not apply. Instead,
`duplicate_label_conflict_probe` asks what *any* model could achieve — 21 mostly-binary
survey answers cannot distinguish 253,680 people:

| quantity | value |
|---|---|
| distinct feature vectors | 227,908 |
| rows sharing a vector with ≥1 other row | **38,000 (14.98%)** |
| duplicate groups | 12,228 |
| groups containing **both** labels | 1,566 |
| rows in conflicted groups | 5,218 |
| unwinnable rows (minority of each conflicted group) | 1,640 |
| **max achievable accuracy on these features** | **0.9935** |

Measured accuracy is 0.8673 — **0.1262 below the bound**, so the ceiling does **not** explain
the shortfall. `duplicate_conflict_note` deliberately refuses to absolve a model that far
below the bound; irreducible error is an explanation only when the model is near it,
otherwise it is an excuse. A test pins that behaviour.

> **Note on a corrected figure:** an earlier hand-written limitation claimed "25,772 rows
> share an identical feature vector". 25,772 is the count of *excess* duplicate rows
> (`df.duplicated().sum()`); the number of rows sharing a vector with at least one other is
> **38,000**. Both are correct answers to different questions; the second is the relevant one.

## 7. Diabetes-specific findings (Phase 5)

### Threshold 0.5 is meaningless here — the 0.1464 recall is the cut-off, not the model

Isotonic calibration maps scores onto true probabilities, and at **13.8% prevalence** a
calibrated probability only exceeds 0.5 for the most extreme profiles. Thresholding there
behaves as a high-precision screen and misses most positives.

- uncalibrated cross-validated recall: **0.795**
- calibrated recall @0.5: **0.1464**
- calibrated recall @0.1388 (≈ prevalence, derived from training): **0.7984** ✔ consistent

`operating_point_note` fires when the two thresholds differ by more than 0.20 recall and
states which row to read. It stays quiet for heart, where 0.5 is a reasonable default.
**ROC-AUC and PR-AUC are threshold-free and are the metrics to compare against other models.**

### SMOTE was measured against class weighting — and lost

Same model, same folds, SMOTE resampling inside each fold's training portion only:

| strategy | ROC-AUC | PR-AUC | recall @0.5 | precision @0.5 | F1 | mean fit s |
|---|---|---|---|---|---|---|
| **class_weight (shipped)** | **0.8301** | **0.4354** | 0.7951 | 0.3065 | 0.4424 | 32.0 |
| smote | 0.8239 | 0.4243 | 0.2899 | 0.5012 | 0.3673 | 65.9 |

PR-AUC **−0.0111** against a fold std of **0.0082**, at **2.1× the fit cost**. The common
"use SMOTE for imbalanced data" advice does not hold here. Recall swings hardest because both
strategies shift the *operating point* rather than the ranking — which is why PR-AUC is the
metric to weigh. Module: `ml/training/imbalance.py`.

### SVC excluded on measured cost — never scored, nothing claimed

Measured fit times on subsamples of the diabetes training set:

| n | fit time |
|---|---|
| 2,000 | 1.07 s |
| 4,000 | 4.27 s |
| 8,000 | 17.52 s |
| 16,000 | 85.09 s |

Empirical exponent ≈ **2.28** → extrapolates to **~7.7 h for a single fit** on the 202,719
training rows and **~23 h for one 5-fold CV pass**, before any hyper-parameter search.
(`SVC` is super-quadratic in n, and `probability=True` adds an internal 5-fold Platt
calibration on top.)

Recorded in `EXCLUDED_MODELS` (`ml/training/model_zoo.py`) and reproduced verbatim in
`reports/diabetes/SELECTION.md` and the model card, so the leaderboard is never quietly
narrower than it appears. **Excluded on cost, not on performance — it was never scored, so
nothing is claimed about how it would have done.**

Random-forest's search space is also narrowed for diabetes only (`n_estimators` 150–400
instead of 200–800) — a cost axis, not a modelling choice; documented in `param_space.py`.

## 7a. Phase 6 — external validation attempted and REJECTED

The heart model was to be validated against **Statlog (UCI id 145)**, a supposedly separate
270-patient cohort. Two checks ran before any metric was believed.

### Check 1 — encoding compatibility: **passed**

The assumption carried since Phase 1, that `cp`/`slope`/`thal` share the Cleveland codes,
**holds**. Value domains are identical (cp 1–4, restecg 0–2, slope 1–3, ca 0–3, thal 3/6/7)
and marginals agree to within ~1 percentage point. Numeric ranges match exactly.

### Check 2 — dataset independence: **failed decisively**

| check | result |
|---|---|
| Statlog rows matching a Cleveland row on **all 13 features** | **270 / 270 (100%)** |
| of those, labels also identical | **270 / 270** |
| rows inside the heart model's own **training** split | **222 (82.2%)** |
| rows inside the heart test split | 48 (17.8%) |
| rows **unseen** by the model | **0** |

Matching is 1:1 and unambiguous — neither dataset contains a duplicate feature vector.
**Statlog is a 270-row subset of the Cleveland database redistributed under a different
name, not a second cohort.**

### Why this matters more than a clean pass would have

Scored naively, Statlog reports **ROC-AUC 0.9399** (PR-AUC 0.9353, recall 0.8333,
accuracy 0.8667, n=270) against the internal test's 0.9535. It lands *slightly below* the
internal score — precisely the modest confirmation a sound external validation produces.
**A fake that looks broken is harmless; this one would have passed review.** It is retained
in `reports/heart/EXTERNAL_VALIDATION.md`, labelled as contaminated and not to be cited.

**Consequence: the heart model has no external validation.** Its only honest performance
estimate remains the 61-row Cleveland test split. This is a negative result and it is the
correct one.

### What was built

- `ml/external/dataset_overlap.py` — reusable independence check: `dataset_overlap()`
  (exact full-vector matching, train/test membership, label agreement, verdict) and
  `schema_compatibility()` (categorical domains, numeric ranges, unit changes).
  `MAX_ACCEPTABLE_OVERLAP = 0.05`. **Run it against any future candidate before calling
  that dataset external.**
- `ml/external/heart_statlog.py` — runs both checks, then scores; returns `status`
  (`validated` / `rejected`) which callers must read.
- `reports/heart/external_validation.json`, `EXTERNAL_VALIDATION.md`,
  `external_schema_check.csv`; `notebooks/external_validation.ipynb`.
- The verdict is written into the heart model card and **survives retraining**
  (`finalize._existing_external_validation` reloads it), so the finding cannot be
  silently dropped by a later run.

> **A bug worth recording.** The first overlap check reported **0% overlap** — a false
> negative in the most dangerous direction. Cause: Cleveland loads as `int64` and Statlog
> as `float64`, so string keys compared `"63"` against `"63.0"` and never matched. Had that
> stood, a fully contaminated dataset would have been certified clean and the fake
> validation published. `row_keys()` now casts to float before comparing, and
> `test_row_keys_match_across_int_and_float_dtypes` pins it.

## 8. Known limitations (per module)

### Heart (n = 303, test n = 61)
- Very small, single-site (Cleveland Clinic), late-1980s cohort. One reclassified patient
  moves accuracy by 1.6 points.
- Referral-based case mix (patients already sent for angiography) → 46% positive rate, far
  above any general population. Probabilities are calibrated to that cohort, not the public.
- `ca` (4 missing) and `thal` (2 missing) are imputed in-pipeline; both are strong predictors.
- `chol == 0` values are almost certainly "not measured" sentinels; left as-is, not treated
  as missing.
- Top features come from tests ordered *because disease is already suspected* — not a
  general-population screen.
- **No external validation** — the intended cohort (Statlog) proved to be a subset of the
  training data (§7a). Nothing establishes that this model transfers to another cohort.

### Kidney (n = 400, test n = 80)
- Single Indian hospital, two-month period. One reclassified patient moves accuracy by 1.25 points.
- **Missingness is confounded with the outcome** — see §6. This is the dominant limitation.
- Classes are near-separable on a few lab values, so near-perfect metrics are a property of
  this dataset, not evidence of a clinically useful model.
- Labels reflect an existing clinical diagnosis and the features include the criteria used to
  make it — the model re-derives the diagnostic rule and has **no prognostic value**.
- Every candidate scores >0.99 CV ROC-AUC, so the algorithm choice is arbitrary.

### Diabetes (n = 253,680, test n = 50,961)
- Self-reported BRFSS 2015 survey answers, **not laboratory measurements**. The target is a
  self-reported *diagnosis*, so undiagnosed cases are labelled negative — the model learns who
  has **been told** they have diabetes, which tracks healthcare access as well as disease.
- Estimates a **risk association**, not a diagnosis and not future onset. The data is
  cross-sectional: no temporal ordering between features and outcome. A high score means
  "resembles respondents who reported diabetes", never "will develop diabetes".
- No survey weighting applied → not nationally representative; the ~14% positive rate is a
  property of this release, not of any population.
- 38,000 rows (15.0%) share a feature vector; the split is grouped so identical profiles never
  straddle it (verified: **0 groups shared across the split**).
- Several top features are plausibly *consequences* of diabetes rather than causes
  (`GenHlth`, `DiffWalk`, `HeartDiseaseorAttack`). SHAP describes the model's use of these
  variables and must **not** be read as causal or as intervention targets.
- Discrimination is moderate (ROC-AUC 0.8317) — treat the probability as a coarse ordering of
  survey respondents, not a per-person risk estimate.

## 9. Open issues carried into Phase 8 (backend)

1. **`RISK_BANDS` are prevalence-agnostic and misleading for diabetes.** The fixed 0.33/0.66
   cut-points in `config.py` encode an implicit assumption of balanced prevalence. Measured
   band distribution on each test set:

   | disease | low | moderate | high |
   |---|---|---|---|
   | heart | 44.3% | 14.8% | 41.0% |
   | kidney | 36.2% | 3.8% | 60.0% |
   | diabetes | **86.8%** | 12.6% | **0.6%** |

   A correctly calibrated 13.9%-prevalence model almost never exceeds 0.66, so "high risk" is
   nearly unreachable and "low" is nearly universal. Options: per-disease bands from the
   training distribution (probability quantiles), bands relative to prevalence, or a
   percentile instead of a band for diabetes. **Deliberately not changed in Phase 5** — it is
   a presentation decision affecting all three modules and the frontend.

2. **The kidney model is an `SVC`**, so SHAP falls back to `KernelExplainer`, which is slow
   per call. A local explanation for a single request is not free the way it is for the
   tree-based heart and diabetes models. Precompute, cache, or accept the latency on
   `/predict/kidney`.

3. **Both pipelines must be loaded per disease at startup**: `pipeline.joblib` (calibrated,
   for probabilities) and `base_pipeline.joblib` (uncalibrated, for SHAP). No model *training*
   in the request path, ever.

4. **No module has external validation.** Heart's attempt was rejected (§7a); kidney and
   diabetes have no compatible second dataset. The API must not imply otherwise — every
   figure it serves comes from one held-out split of one dataset.

## 10. Next step — Phase 7: Calibration + fairness subgroup analysis

1. **Calibration** — the per-disease wrapper is already selected and shipped (§5). Phase 7
   finalises the reporting: store calibration curves and pre/post Brier in
   `reports/<disease>/calibration/`, which already holds the selection and test tables.
2. **Fairness** — build `ml/fairness/subgroup_metrics.py`: recall, specificity, precision
   and ROC-AUC broken down by **sex** (heart, diabetes) and **age bands** (all three).
   Output `reports/<disease>/fairness/subgroups.csv` plus notes.

Constraints to hold to:

- **Never label a model "fair".** Report disparities and their uncertainty.
- Subgroup sample sizes are brutal: heart's test set is 61 patients total, kidney's is 80.
  A per-sex or per-age-band estimate there rests on single-digit counts and must carry that
  caveat prominently — or be reported as not estimable. Diabetes (50,961 test rows) is the
  only module where subgroup metrics will be stable.
- Kidney has no sex variable → age bands only.
- The same discipline as every prior phase: if a subgroup result is too noisy to mean
  anything, say so rather than publishing a number that looks like a finding.

Do **not** force external validation for kidney or diabetes — no compatible dataset exists,
and inventing one would violate §1. Any future candidate must first pass
`ml.external.dataset_overlap.dataset_overlap()`.
