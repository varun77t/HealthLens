# Frontend — v1 (guided form + worked examples)

> **For research and educational purposes only. Predictions generated by this system are
> based on machine-learning models trained on historical public datasets and must not be
> interpreted as medical diagnosis or professional medical advice.**

```bash
uvicorn backend.main:app --port 8000     # terminal 1
npm --prefix frontend run dev            # terminal 2  ->  http://localhost:5173
```

The dev server proxies `/api` to `127.0.0.1:8000`, so development never depends on the CORS
allow-list. For a build, set `VITE_API_BASE` to the API origin.

Vite + React 18 + TypeScript + Tailwind. No component library and no charting library — the
SHAP bars are ~30 lines of CSS. Production bundle is 191 KB (61 KB gzipped).

---

## Why a form first, and not the document upload

The upload-and-OCR flow is the eventual headline, but it cannot be v1, because **no
document-based entry mode can complete any of the three models**:

| model | best case from a perfect document | still missing |
|---|---|---|
| kidney | ~20 of 24 from urinalysis + CBC + metabolic panel | appetite, pedal edema, anaemia, history flags |
| heart | 5 of 13 from a blood panel | `thal`, `ca`, `cp` — the three highest-impact fields |
| diabetes | ~5 of 21 | `GenHlth`, Income, Education, diet, activity |

Every path ends at a form for the remainder, and the review screen *is* that form with values
pre-filled. So paste-text (v2) and OCR upload (v3) are pre-fills for what v1 builds, not
alternatives to it. Nothing here gets thrown away.

## The flow

```
Dashboard (3 cards)  ->  Intake (grouped form)  ->  Review  ->  Result
                              ^                        |
                              +---- change an answer ---+
```

Routes: `/`, `/:disease`, `/:disease/review`, `/:disease/result`. Session state lives in
memory only — nothing entered is written to `localStorage` or persisted anywhere, and any
edit invalidates a prediction made from the previous values, so the result screen can never
show a number computed from inputs the user has since changed.

### Step 0 — pick one module

Three cards, each with its real test ROC-AUC, training size and external-validation status.
Choosing kidney means the app never asks a single diabetes survey question. That one screen
does more for the field count than any other decision.

### Intake — 58 fields made to feel like 8

The form is **generated** from `GET /models/{disease}/schema`. No input, label, option list
or bound is hand-written, so a retrain cannot leave the UI describing a model that no longer
exists.

Three levers:

1. **Grouped by where the paper is**, not by what the model wants — *About you · Vitals ·
   Symptoms · Your medical history · From your blood test · From your urine test · From a
   resting ECG · From an exercise stress test · From cardiac imaging · Wellbeing · Lifestyle ·
   Healthcare access*. Each group collapses and shows its own progress.
2. **Key fields only**, on by default. `tier` is computed from the model's own SHAP output:
   *core* is the smallest set covering 80% of total mean |SHAP|. That is **7 / 8 / 7 fields**
   for heart / kidney / diabetes — not 13 / 24 / 21.
3. **Coverage weighted by attribution mass.** The progress bar sums `shap_mass_share`, so for
   kidney, supplying urine specific gravity (16.4% of the mass) moves it eighty times further
   than urine sugar (0.2%). "12 of 24 fields" would imply every field is worth the same.

**"I don't have this" is a first-class answer** next to every field, distinct from an empty
box. Both reach the model as missing, but only one is a decision, and the review step refuses
to run while anything is merely untouched.

### Review — nothing is predicted before this

Rows ordered by `shap_rank`, so attention goes where a wrong value would change the answer
most. Each row shows **✓ Confirmed**, **— Unavailable**, or **⚠ Not answered**, and expands
in place for editing. The run button stays disabled while any field is unanswered, with a
one-click *"I don't have any of these"* for the remainder.

### Result — the decision, not the probability, is the headline

> **This model would flag this case for follow-up.**
> Estimated probability 14.5% · Decision threshold 13.9% · Presentation band High

That ordering is deliberate. A bare probability invites the reader to apply a mental 50%
cut-off; for diabetes that would turn a recall of 0.7984 into 0.1464. The threshold and the
rule that produced it are on screen next to the number.

Also on the page: which fields were imputed and named individually, anything outside the
training range, every warning the API returned (no external validation; the case's own
age-band recall and specificity where Phase 7 measured it reliably), the SHAP contributions
with human-readable values, and the model's full limitations list from its card.

### Worked examples

`GET /samples/{disease}` returns real rows **from the held-out test split** — records the
model was never fitted on — two with the outcome recorded as positive and two as negative.
One click fills the form. The result page says plainly that one case agreeing or disagreeing
with the model proves nothing either way, and points at the test-set size behind the card's
metrics. A test asserts every exported sample really is a held-out row.

## Defects found by running it

Three things were wrong and were fixed before this was called done:

1. **Ordinal survey codes rendered as number boxes.** `Age`, `GenHlth`, `Education` and
   `Income` are 1-13 / 1-5 / 1-6 / 1-8 scales the pipeline treats as numeric, so they had no
   options — the form asked people to type `8` for their age band. They now render as
   labelled dropdowns while still sending the number. `options_for` raises if any level
   inside the observed training range has no label, because an unlabelled level would be
   unselectable despite appearing in the training data.
2. **Scroll position carried across routes**, landing the user below the decision headline
   after confirming from a scrolled review table.
3. **The auto-opened group could be one that was filtered out.** For kidney the first group
   by order is *About you*, which contains no key field, so in the default "key fields only"
   mode every visible section rendered collapsed.

## Colour

Status colours are deliberately not red/green. A model flag is not a diagnosis and colouring
it like a pass/fail test would overstate what the number means.
