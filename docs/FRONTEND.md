# Frontend — sign in, then the upload-first assessment flow

> **For research and educational purposes only. Predictions generated by this system are
> based on machine-learning models trained on historical public datasets and must not be
> interpreted as medical diagnosis or professional medical advice.**

```bash
python -m alembic upgrade head           # once: creates data/app.db
uvicorn backend.main:app --port 8000     # terminal 1
npm --prefix frontend run dev            # terminal 2  ->  http://localhost:5173
```

The dev server proxies `/api` to `127.0.0.1:8000`, so development never depends on the CORS
allow-list. For a build, set `VITE_API_BASE` to the API origin.

Vite + React 18 + TypeScript + Tailwind. No component library, no charting library.
Production bundle 233 KB (72 KB gzipped).

**Authentication is mandatory.** Nothing below `/app` renders without a session, and the
API refuses every request without one. Account design, session handling and the
saved-analysis contract are in [AUTH.md](AUTH.md); this document covers the screens.

## The flow

**Landing → sign in → choose → upload → review → analyse → explain → report → save.**
The guided form is the fallback, behind *"Don't have a report? Enter information
manually"*, and saving is a separate opt-in at the end.

```
Manual form ──┐
Paste text ───┼──► REVIEW (verified data) ──► /predict ──► explain ──► report PDF
Upload PDF ───┘        ^ same component, same request
```

That convergence is the architecture. Upload, paste and manual entry all write the same
session state, the review screen is the single verified-data surface, and every path produces
a byte-identical backend request. It is also why the guided form was built first: no
document-based entry mode can complete *any* of the three models on its own —

| model | best case from a perfect real report | still missing |
|---|---|---|
| kidney | ~20 of 24 from urinalysis + CBC + metabolic panel | appetite, pedal edema, anaemia, history flags |
| heart | 5 of 13 from a blood panel | `thal`, `ca`, `cp` — the three highest-impact fields |
| diabetes | ~5 of 21 | `GenHlth`, Income, Education, diet, activity |

— so every path ends at a form for the remainder. For the controlled demonstration the
synthetic reports carry the complete feature set, which is what makes a clean upload-only
run possible at all.

### Routes

**Public — the whole list:**

| route | screen |
|---|---|
| `/` | landing: what this is, what it is not, and one thing to do |
| `/signin` · `/signup` | accepts `?next=` |
| `/forgot` · `/reset/:token` | password reset |

**Protected — everything else, behind one `<RequireAuth>`:**

| route | screen |
|---|---|
| `/app` | "Welcome back, — / What would you like to check?" then module selection |
| `/app/:disease` | upload-first entry, sample reports, manual fallback |
| `/app/:disease/enter` | the guided form |
| `/app/:disease/review` | "We found your information" — verify before anything runs |
| `/app/:disease/result` | risk category, plain-language factors, disclosures, **save** |
| `/app/:disease/about` | the full research layer: dataset, metrics, limitations |
| `/app/history` · `/app/history/:id` | saved analyses |
| `/app/account` | sessions, password, what is stored, delete account |

The gate is a single wrapper in `App.tsx`, not a check inside each page. A page that forgot
to check would render a health-data form to someone with no account and nothing would
notice; here, an unprotected route has to be written outside that element on purpose.

**The intended destination survives the redirect.** `/app/kidney` →
`/signin?next=%2Fapp%2Fkidney` → through sign-up if you follow *"Create one"* → back to
`/app/kidney`. `next` is validated before use: an unvalidated one is an open redirect that
would bounce someone off-site immediately after they typed their password. Only paths inside
`/app` are accepted — a scheme, a protocol-relative `//host`, a backslash, or
`/application-elsewhere` all fall back to `/app`.

**Working state is still in memory only.** Nothing entered or extracted is written to
`localStorage`, uploaded documents are never stored, and any edit invalidates a prediction
made from the previous values — so the result screen cannot show a number computed from
inputs that have since changed. What changed in Phase 11 is that there is now *one* way for
health values to reach a database: the explicit **Save to my history** control. Being signed
in stores nothing; running an assessment stores nothing.

## Screens

### Module selection

Three cards, plain copy, no metrics. ROC-AUC, training counts and external-validation status
sit in a **"How these estimates are produced"** disclosure at the foot of the page. On the
primary journey they were answering a question nobody had asked yet, and they made a health
tool read like a benchmark table.

### Entry

A single large dropzone, PDF only. The promise made is deliberately modest — *"the
information available in your report"* — because real documents do not contain every field a
model uses, and a screen that implies otherwise sets the review step up to look like a
failure rather than the point.

Sample reports are downloadable here for demonstrating the flow. The recorded outcome is
**not** shown next to them: download one, run it through, then compare.

### Review — nothing is analysed before this

Grouped the way information physically arrives (*About you · Vitals · Symptoms · Your medical
history · From your blood test · From your urine test*), not by model importance, because
this screen is read against a document in your hand. Every row shows the human label, the
value with its unit, a status, and an **Edit** control that expands in place.

| status | meaning |
|---|---|
| **✓ Found** | read cleanly from the document |
| **✓ Confirmed** | you typed or accepted it |
| **⚠ Please verify** | read, but not confidently |
| **⚠ Needs review** | not found, and not yet settled |
| **⚠ Check units** | outside the range the model was trained on |
| **Not available** | you said you don't have it |

The **Analyze** button does not appear while anything is still *Needs review*. A one-click
*"I don't have any of these"* settles the remainder.

Per-field provenance sits behind a **Source** control: the page it came from and the exact
line it was read out of. Available without turning the screen into a parser log.

### Result

```
ESTIMATED RISK
High
100.0% estimated probability
Above the threshold this model uses (57.9%)
```

Then *"What influenced this estimate?"* as plain sentences with a direction —
**Random blood glucose** 423 mg/dL, *pushed the estimate higher* — followed by what the
analysis did and did not know, the report download, and three disclosures: **How was this
estimated?** (model, threshold, band boundaries, raw SHAP values, methodology note),
**Caveats that apply to this result**, and **Known limitations of this model**.

### The public screens

Written for someone who has never seen the project and does not care how it works. No
"model", no "dataset", no "assessment", no build details — the landing page is a headline,
one sentence, two buttons and three steps. The research layer was not deleted; it is behind
the sign-in, on each module's own page, which is where someone who wants it will look.

The one thing kept on the surface is that this cannot diagnose anything, in those words. It
is the sentence a first-time visitor most needs and least expects, and it does not survive
being phrased carefully.

Two things came off these screens outright: the wordmark tagline ("Explainable health risk
analysis" describes the project to someone who already knows what it is) and a note on the
password-reset screen telling the reader to check the terminal running `uvicorn` — a build
detail on a page a stranger reads.

### Saving and history

Saving is opt-in, at the end, and says what it keeps before it is pressed — the values, the
estimate, and the model version and threshold that produced it; not the document. The page
sends the **inputs**; the server re-runs the model and stores its own answer, so nothing in
a saved entry is a number the browser reported.

`/app/history` lists what you chose to save, newest first, filterable by module. Every row
shows the percentage **next to the threshold that defined its category** — "14.5%" against
diabetes's 13.9% means the model flagged the case, and a list is exactly where someone skims
a number out of context.

An entry produced by a model version that is no longer live is marked *Earlier model*, and
its detail page explains that the result has not been re-scored, because that would
attribute a new model's decision to an old record. Only the label can be edited: the values
and the result are a record of what was run, not a draft.

### Account

Signed-in browsers, password change, account deletion, and a plain statement of what the
account stores — including that there is no encryption at rest, which is a deployment
property this application cannot honestly claim on its own.

### About

The research layer in full: dataset provenance, model and selection rationale, measured
performance at both thresholds, the performance-attribution probe, explainability method,
limitations and out-of-scope uses. Nothing was deleted to simplify the primary journey — it
was moved here, reachable from every screen.

## Two deliberate departures from the brief

**The category is the headline, not the percentage.** The brief asked for
`Estimated risk / XX% / [category]`. The screen shows the category large with the percentage
beneath and one line of context. The category's upper boundary **is** the model's operating
threshold, so it cannot contradict the model's decision — whereas a bare percentage read
against an assumed 50% can. For diabetes that is the difference between recall 0.7984 and
0.1464: "14.5%" looks reassuring and means the opposite.

**The dropzone advertises PDF only.** The brief listed "PDF, JPG or PNG". Image extraction is
not implemented, so the server answers a JPG with a 415. An affordance that does not work is
worse than one that is absent: the dropzone says PDF, and dropping an image gets a specific
message pointing at manual entry rather than a generic failure.

## Extraction in the UI

`fromExtraction` maps each extracted field to a form status: `found` → **✓ Found**,
`needs_review` → **⚠ Please verify**, anything absent → **⚠ Needs review**.

A field the document did not yield becomes *unsettled*, **not** *unavailable* — even when the
report explicitly said "Not performed". Both reach the model as missing, but only the first
blocks the run, so the person makes that call rather than inheriting it from a parser. For
kidney that is not a formality: its missingness is confounded with the outcome, and a
model trained on missingness indicators alone reaches ROC-AUC 0.8023 on that test set.

## Density: what came out of the primary path

Removed from the main journey per the redesign brief: the coverage meter, "key field" badges,
feature-count percentages, ROC-AUC and training counts on the landing screen, raw SHAP
values, and the long explanatory paragraphs.

**Almost none of it was deleted** — metrics and methodology moved to `/:disease/about` and to
the result page's disclosures. Two things genuinely went: `CoverageMeter.tsx` and the coverage
helpers in `lib/intake.ts`. The honest-progress-bar argument they existed for was sound, but
it is not worth a dashboard aesthetic on a screen where someone is reading about their own
health.

Status colours are deliberately not red/green. A model flag is not a diagnosis, and a
pass/fail palette would assert far more than the number supports.

## Defects found by running it

Nine, across four passes — every one found by running the thing, not by reading it.

1. **Ordinal survey codes rendered as number boxes.** `Age`, `GenHlth`, `Education` and
   `Income` are 1-13 / 1-5 / 1-6 / 1-8 scales the pipeline treats as numeric, so they had no
   options — the form asked people to type `8` for their age band. Now labelled dropdowns
   that still send the number; `options_for` raises if any level inside the observed training
   range is unlabelled, since that would make a real training value unselectable.
2. **Scroll position carried across routes**, landing users below the result headline.
3. **The auto-opened group could be one filtered out** by the old "key fields only" mode —
   for kidney, every visible section rendered collapsed.
4. **A section heading swallowed the field below it.** "RESTING ELECTROCARDIOGRAM" is a
   legitimate alias for `restecg`, sits above the data row and carries no value, so the
   first-match-wins rule lost the real reading. Matches are now ranked by evidence strength.
5. **`N/A` did not register as "not measured".** Normalisation strips punctuation to
   whitespace, so `n/a` became `n a` and missed the literal set. Both sides now normalise
   through the same function.
6. **A number was harvested from anywhere in the remainder.** "Cholesterol checked in the
   last 5 years — Yes" prefix-matches the `chol` alias, and the parser then took the `5`
   out of "5 years" as a cholesterol reading. The number must now follow its label
   directly; found by cross-uploading a diabetes report to the heart module.
7. **A range was halved.** "Age group 75-79" yielded a heart age of `75` marked *found*,
   claiming a precision the document does not have. A bare range where a single value is
   expected is now refused.
8. **A transient API failure signed the user out.** `AuthProvider` treated any `/auth/me`
   error as "not signed in". The API takes ~15 s to load three pipelines and a
   KernelExplainer, so a page opened in that window got a proxy error and a perfectly valid
   session was bounced to the sign-in screen. Now retried once — and `checking` is a third
   state distinct from `anonymous`, without which reloading any protected page flashed the
   sign-in screen before bouncing back. Found by noticing two 500s in the console that never
   reached uvicorn.
9. **A saved analysis could crash its own detail page.** It renders feature labels from the
   *current* schema, but pinning the model version exists precisely so a record can outlive
   the schema that produced it. A feature the schema no longer knows now renders its stored
   value instead of throwing on the lookup.

## Verified in-browser, all three modules

Each uploaded through the real dropzone, reviewed, analysed, and the report downloaded.

| module | read | gate | result | report |
|---|---|---|---|---|
| kidney | 21/24, 3 not found | held on 3 | **High** · 100.0% · above 57.9% | 200 |
| heart | 13/13 | none needed | **High** · 69.0% · above 64.4% | 200 |
| diabetes | 21/21 | none needed | **High** · 14.5% · above 13.9% | 200 |

No console errors on any run. Heart is the best explanation demo of the three: its factors
split both ways — *Thallium scan result: Normal* and *Sex: Female* push the estimate **down**
while vessels, chest pain type and ST depression push it up. Diabetes is the best argument
for the design: 14.5% against a 13.9% threshold reads as reassuring to anyone applying a
mental 50% cut-off, and means the opposite.

### Cross-module safety

Uploading a report to the wrong module is refused field by field rather than partly accepted.
Only genuinely shared measurements carry across — `age` in years, and `sex`, which uses the
same 0/1 convention in both models that record it. Everything else comes back flagged with a
reason. The case that matters: heart records age in years while diabetes uses a 1-13 band
code, so *"Age 62 years"* into the diabetes module yields **no value** and lists the bands it
would accept.

### Signed in, verified in the browser

Sign-up through the real form with `?next=%2Fapp%2Fkidney` preserved end to end; upload,
review, analyse, save, list, open, sign out, redirect. `document.cookie` is empty on every
screen — the session is genuinely unreadable from JavaScript. The four open-redirect cases
above were checked against the running app, not only in the source.

`npx tsc --noEmit` clean · `npm run build` clean · `python -m pytest -q` **387 passed**.
