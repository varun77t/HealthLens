# API reference — Phase 8

> **For research and educational purposes only. Predictions generated by this system are
> based on machine-learning models trained on historical public datasets and must not be
> interpreted as medical diagnosis or professional medical advice.**

```bash
uvicorn backend.main:app --reload
```

Interactive docs at `/docs`, machine-readable schema at `/openapi.json`.

Startup loads three pipelines, three model cards and three SHAP explainers — measured at
about **7 s**, dominated by the kidney `KernelExplainer`. After that, **no request path
fits, trains, resamples or reads a dataset.**

---

## Prerequisites

The API reads only from `models/<disease>/`. It never touches `data/`. Two files per disease
are produced after training by:

```bash
python -m scripts.export_serving_assets
```

| file | purpose |
|---|---|
| `serving.json` | operating threshold, risk bands, per-feature ranges and categories, explainer profile, external-validation status |
| `shap_background.joblib` | the exact 200 training rows the training run's explainer used (same `RANDOM_STATE`, same sample) |

Ranges come from the **training** split only. The test split is never consulted, so nothing
the API advertises was derived from held-out data.

---

## Endpoints

| method | path | purpose |
|---|---|---|
| `GET` | `/health` | service and per-module status |
| `GET` | `/models` | model-card summary for all three modules |
| `GET` | `/models/{disease}` | the full `metadata.json`, verbatim |
| `GET` | `/models/{disease}/schema` | input feature dictionary: bounds, groups, tiers, option labels |
| `GET` | `/samples/{disease}` | worked example cases from the held-out test split |
| `POST` | `/predict/{heart\|kidney\|diabetes}` | score one case |
| `POST` | `/scenario/{disease}` | score the same case again with changed inputs |
| `GET` | `/analytics/{disease}` | saved metrics, model comparison, SHAP, calibration, fairness |
| `GET` | `/analytics/{disease}/figures/{name}` | one saved evaluation figure (PNG) |

Three separate `/predict` routes, not one generic endpoint. The modules share no features
and no cohort; separate routes keep the OpenAPI schema honest about that and make it
impossible to submit heart features to the kidney model. **There is no combined endpoint and
no aggregate health score.**

## Reading a prediction

```jsonc
{
  "probability": 0.3666,          // calibrated
  "flagged": false,               // the model's DECISION, at its own threshold
  "threshold": 0.6435845785678462,
  "threshold_rule": "Youden's J ... maximised on out-of-fold predictions over the TRAINING set ...",
  "risk_band": { "label": "moderate", "lower": 0.3218, "upper": 0.6436, "note": "..." },
  "imputed_features": [],
  "extrapolated_features": [],
  "warnings": [ /* ... */ ],
  "explanation": { /* ... */ },
  "disclaimer": "..."
}
```

### `flagged` is the decision; `risk_band` is a label

They are reported separately so the label cannot be mistaken for the decision. Both are
anchored on the same boundary: `flagged == (risk_band == "high")` by construction, and a
test pins it.

### The threshold is never 0.5

Each model's operating threshold was learned by Youden's J on **training** out-of-fold
predictions and applied unchanged to the test set.

| module | threshold | test recall @ threshold | test recall @ 0.5 |
|---|---|---|---|
| heart | 0.6436 | 0.8214 | 0.8929 |
| kidney | 0.5792 | 0.9600 | 0.9600 |
| diabetes | **0.1388** | **0.7984** | **0.1464** |

A caller that ignores `threshold` and applies 0.5 to the diabetes probability gets a
different and much worse classifier — recall 0.1464 instead of 0.7984.

### Risk bands are anchored on that threshold, not on a fixed grid

The platform previously used fixed cut-points (low < 0.33, moderate, high ≥ 0.66). Measured
on the diabetes test set (n = 50,961), that grid put **44,243 rows (86.8%) in "low" and 283
(0.56%) in "high"** — and labelled *every case the model flags*, including every true
positive it catches, as "low" or "moderate". The label contradicted the model.

Bands are now `[0, t/2)`, `[t/2, t)`, `[t, 1]` for each model's own `t`. Only the upper
boundary means anything; the lower one is an arbitrary split of the remaining range, and the
`note` field on every response says so.

### The explanation explains the *uncalibrated* model

SHAP runs on `base_pipeline.joblib`; `probability` comes from the calibrated wrapper.
The response returns both `uncalibrated_probability` and the calibrated `probability`
rather than implying the contributions sum to the latter. Calibration is a monotonic
transform of the base score, so signs and ranking carry over; magnitudes do not.

| module | explainer | measured cost per call |
|---|---|---|
| heart | `TreeExplainer` | ~44 ms |
| diabetes | `TreeExplainer` | ~48 ms |
| kidney | `KernelExplainer` (the selected model is an SVC) | **~0.4-0.8 s** |

Pass `?include_explanation=false` to skip it. `/scenario` defaults to `false` because it
scores twice.

Those figures are re-measured on every `export_serving_assets` run and recorded in each
`serving.json`; the kidney number in particular moves by a factor of two between runs on the
same machine, so treat it as an order of magnitude rather than a benchmark. `GET /models`
always reports the value from the last export.

### Every response states the external-validation position

No module has external validation. Heart's intended external cohort (Statlog, UCI 145) was
tested in Phase 6 and **rejected** — all 270 rows match a Cleveland row exactly, 82.2% of
them inside heart's own training split. Every performance figure in this platform comes from
a single held-out split of a single dataset.

### Diabetes predictions carry their age band's measured error profile

One global threshold does not behave the same way in every age band (Phase 7, at t = 0.1388):

| age band | n | recall | specificity |
|---|---|---|---|
| 18-34 | 4,848 | 0.2689 | 0.9852 |
| 35-49 | 10,111 | 0.6109 | 0.8806 |
| 50-64 | 18,110 | 0.7820 | 0.7099 |
| 65+ | 17,892 | 0.8603 | 0.5019 |

The response reports the row matching the case's own age band. Heart and kidney report
nothing here: only 1 of 6 and 0 of 4 of their subgroups were reliable on 61 and 80 test
rows, and an unreliable subgroup contributes silence, not noise.

## Input validation

Every field is optional — the pipeline's imputers were fitted on the training folds, so a
missing value is handled the way training missingness was. Three levels of response:

| condition | result |
|---|---|
| value outside the mechanical envelope (one observed range either side of the training min/max) | **422** |
| unrecognised categorical level | **422** |
| unknown field name | **422** |
| no fields at all | **422** |
| value inside the envelope but outside the observed training range | **200**, listed in `extrapolated_features` |
| field omitted | **200**, listed in `imputed_features` |

Unknown categories are rejected rather than warned about because the one-hot encoder runs
with `handle_unknown="ignore"`: an unrecognised level is encoded as all-zeros and would yield
a confident-looking prediction for a case whose category the model never saw.

An empty body is refused because it describes no case — the result would be the imputed
training-median profile, not a prediction. A partially specified case *is* a legitimate
question and is answered, with the imputation reported.

The envelope is mechanical, **not clinical**: it encodes no medical knowledge about which
values are physiologically possible. `GET /models/{disease}/schema` returns both the observed
training range and the accepted envelope for every feature.

## `POST /scenario/{disease}`

```jsonc
{ "features": { /* the base case */ }, "overrides": { "BMI": 40.0 } }
```

Both estimates come back side by side. There is no single "improved risk" number, and every
response leads with:

> Illustrative model scenario — shows how the trained model responds to changed inputs. It
> is not a prediction of real medical risk, and not a statement that changing the input
> would change anyone's health. The model is a cross-sectional association fitted to
> observational data; it supports no causal claim.

Overriding a feature that is plausibly a *consequence* of the disease, or is not modifiable
at all, adds a warning naming that feature — `GenHlth`, `DiffWalk` and `PhysHlth` for
diabetes; `thal`, `ca`, `oldpeak`, `exang` for heart; `sc`, `hemo`, `pcv`, `sg`, `al` for
kidney; `age` and `sex` everywhere. Base case and overrides are validated separately against
the same schema as `/predict`, so an out-of-range override is reported as an override error
rather than blamed on the base case.

## `GET /analytics/{disease}`

Reads `reports/<disease>/` verbatim: `metrics.json`, `model_comparison.csv`,
`threshold_sweep.csv`, `shap_global.json`, `calibration/summary.json`,
`fairness/disparities.json`, and the list of figure filenames. **No metric is recomputed at
request time**, so the API cannot report a number that no experiment produced —
`test_analytics_serves_the_metrics_that_were_written_to_disk` asserts byte-equality with the
file on disk.

Figures are served by matching the requested name against the files actually present in the
directory rather than by joining it onto a path, so a crafted name cannot escape.

## Deployment notes

CORS defaults to `http://localhost:5173,http://localhost:3000` for local development and is
overridden with the `ALLOWED_ORIGINS` environment variable. A wildcard origin is not a
deployment setting and is not the default.

There are no secrets, no API keys and no database. Everything the service reads is a
committed artifact or a locally regenerable one.
